# ADR-0007: Versioning strategy

## Status

Accepted

## Date

2026-09-10

## Context

`vc.Ifx` is a framework-level suite with multiple NuGet packages. The suite needs a predictable versioning model that makes package compatibility, breaking changes, target framework support, and API lifecycle status clear to both maintainers and consumers.

Without a clear policy, versioning pressure can lead to unnecessary project splits such as `V1`, `V2`, `Net8`, or `Net10` projects. That makes the framework harder to consume and maintain. Versioning should remain boring, explicit, and compatible with normal NuGet expectations.

## Decision

We will use NuGet package versions with Semantic Versioning.

- Patch versions, such as `1.2.3`, are for compatible bug fixes.
- Minor versions, such as `1.3.0`, are for backwards-compatible features.
- Major versions, such as `2.0.0`, are for intentional breaking changes.

We will keep one project per package responsibility, not one project per version. Examples:

- `vc.Ifx.Filtering`
- `vc.Ifx.Querying`
- `vc.Ifx.Proxy`
- `vc.Ifx.WebApi`
- `vc.Ifx.Analyzers`

We will not create project names such as `vc.Ifx.Filtering.V1`, `vc.Ifx.Filtering.V2`, `vc.Ifx.Net8`, or `vc.Ifx.Net10` unless there is a concrete need to support two incompatible APIs at the same time.

Target framework support is handled through project target frameworks, not package name changes. Runtime libraries should target the latest stable .NET by default. Multi-targeting is allowed when consumers require supported older frameworks:

```xml
<TargetFrameworks>net8.0;net10.0</TargetFrameworks>
```

Analyzer, code fix, and source generator implementation packages may target `netstandard2.0` when Roslyn host compatibility requires it. Public generator attributes may live in a separate abstractions package so consumers can reference annotations without depending on generator implementation details.

Breaking changes should follow an API lifecycle:

1. Add the replacement API beside the old API when practical.
2. Mark the old API with `[Obsolete]`.
3. Keep the old API for at least one major-version transition when practical.
4. Remove the old API in the next major version.

Use code labels to communicate lifecycle state:

```csharp
[Obsolete("Use FilterSpec<T> instead. This API will be removed in vc.Ifx.Filtering 2.0.")]
public sealed class FilterBuilder<T>
{
}
```

Use experimental labels for APIs that are not yet stable:

```csharp
[Experimental("IFXEXP001")]
public sealed class FilterSpec<T>
{
}
```

Each package should maintain release notes or a changelog that separates breaking changes, new features, fixes, and migration guidance.

## Consequences

### Positive

- Consumers can rely on standard NuGet and SemVer expectations.
- Package names stay stable and aligned to responsibility.
- Breaking changes are visible through major versions instead of project-name churn.
- API migration paths are explicit through `[Obsolete]`, `[Experimental]`, and changelog entries.
- Target framework support stays a build/package concern instead of fragmenting the source tree.

### Negative

- Maintainers must be disciplined about identifying breaking changes before release.
- Some obsolete APIs may remain in the codebase temporarily to support migration.
- Multi-targeting can increase build and test time when older frameworks must be supported.
- Experimental APIs require clear follow-through: stabilize, change, or remove them.

## Alternatives considered

- Create separate projects for each breaking-change generation.
  - Rejected because it increases project count and makes normal package consumption harder.
- Encode target frameworks in package or project names.
  - Rejected because NuGet and MSBuild already support target framework selection.
- Avoid formal versioning until the suite is stable.
  - Rejected because framework-level packages need migration clarity early, especially while APIs are being modernized.
- Remove old APIs immediately whenever replacements are added.
  - Rejected because it makes adoption harder and reduces trust in the framework package lifecycle.
